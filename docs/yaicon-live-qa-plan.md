# 11월 25일 YAICON 관객 질의응답 설계안

> 작성 기준은 2026년 11월 24일 KST, 발표일은 11월 25일 KST, 저장소 기준은 `main 8a9d901`이다. GPT‑6.2 Astra High의 설계 초안에 저장소·Orbit 확인과 발표일 검색 재현을 합쳤다.

**권장 흐름은 한국어·영어 마이크 입력 → 프로젝트 근거 검색 → 젠슨 황의 공개 설명 방식으로 영어 답변 → 젠슨 황 참조 영어 음성 + 한국어 자막이다.** 마이크 인식 언어와 자막 연결 상태로 답변 언어가 바뀌는 현재 의존성을 끊는다. 발표 전에는 개요와 실제 아키텍처를 안정적으로 맞히는 것, 팀의 선택 이유와 기술적 추론을 정확히 구분하는 것, 구글이 응답하지 않아도 오디오가 계속되는 것을 우선 검증한다.

## 1. 무대에서 관객이 경험할 한 턴

관객이 한국어나 영어로 질문한다. 진행자는 화면에 표시된 전사를 확인하고 필요시 고쳐 보낸다. 아바타는 영어로 핵심부터 말하며, 그 문장이 실제로 재생되는 동안 한국어 자막을 표시한다. 질문이 “우리 프로젝트를 소개해 주세요”라면 팀이 무엇을 만들었는지, 관객이 무엇을 보고 듣는지, 어떤 근거로 답하는지 설명해야 한다. “젠슨, 불확실한 문제를 어떻게 시작하나요?”라면 출처가 있는 인터뷰에서 관련 사고방식을 찾아 답한다. “젠슨이 이 알고리즘을 직접 만들었나요?”에는 학생 팀의 구현과 시뮬레이션 속 화자의 역할을 분명히 밝힌다.

무대 프리셋에서 질문의 언어 선택과 답변의 언어 정책을 독립시킨다. 입력은 ko 또는 en, 답변과 음성은 en, 자막 목표는 ko다. KO/EN 지원은 우선 진행자가 입력 언어를 선택한다는 뜻으로 정의한다. 기존 ASR에 검증된 언어 자동 감지가 있으면 별도로 열 수 있다. 실시간 동시 통역이나 한국어 목소리까지 약속할 필요가 없다. 마이크가 실패해도 전사 편집·텍스트 입력으로 같은 검색과 영어 응답을 이용할 수 있어야 한다. 관객 화면에는 AI 시뮬레이션 표시를 유지한다.

## 2. 현재 어디까지 되는가

- 조사 기준은 원격 main과 로컬 main에서 같은 8a9d901cb6a168d4fe8de59086705a8bedadd115이다. 당시 시연자가 띄운 프로세스, 로컬 모델 파일 또는 private checkout 식별은 별도다. PR #28의 workbench가 준비한 별도 checkout을 가리킬 수도 있다. 시작 전 실제 실행 경로, 체크아웃 SHA, 비밀값을 제거한 공급자 식별, 모델/참조 해시, 선택한 API 경로를 한 장에 남긴다.
- PR #30의 data/qa/project.json은 10개 카드, news.json은 2개다. 프로젝트 카드는 11월 28일 23:40 KST까지 유효해도 두 역사적 상태 카드는 #27/#29가 열려 있었던 11월 21일을 가리킨다. 이후 둘 다 병합됐고 #31/#32도 main에 들어왔다. 날짜만 현재로 바꾸면 잘못된 답을 더 오래 허용한다. 뉴스는 11월 23일 23:40 KST 만료, 시연일엔 최신 근거로 쓸 수 없다. 프로젝트 질의가 우선인 시연에는 기존 만료 처리를 두고 뉴스 갱신을 독립 작업으로 둔다.
- '우리 프로젝트'는 프로젝트 분류 단어이나 소개 카드와 내용 cue가 없어서 '우리 프로젝트를 소개해 주세요'는 자료가 없다는 경로로 간다. '프로젝트 파이프라인'처럼 정확한 단어를 쓰면 맞는다. 현재 src/bias/qa_knowledge.py는 NFKC 정규화, KO 부분 문자열/EN 단어 경계, cue 합산 점수, 동률 ID 정렬, 상위 3장이다. BIAS_QA_KNOWLEDGE_DIR가 빠지면 이 분기 자체가 꺼지고, 일반 페르소나 경로의 가정적 답변이 프로젝트 사실처럼 들릴 수 있다.
- src/bias/engine.py에서 프로젝트 분기는 knowledge_events 호출 뒤 반환한다. 기본 페르소나 그래프·적응형 길이 정책 변경이 이 응답에 저절로 적용되지 않는다. src/bias/qa_dialogue.py의 프로젝트 경로에는 별도 2~3문장 프롬프트가 있고, Why Qwen은 reason=undocumented_model_rationale 전용 고정 답변으로 막혀 있다. 파일에만 카드를 추가해도 말투, 이유 설명과 위험한 추정 문제는 해결되지 않는다.
- 현재 모델 응답은 허용된 인용 ID·형식을 검사하되 의미 지지는 unreviewed이다. 토큰과 음성용 segment가 최종 결과 검사보다 먼저 흐른다. 이후 화면의 경고만으로 먼저 말한 잘못된 수치를 되돌릴 수 없다. 라이브에서 근거와 추정을 엄격히 구분할 때는 음성 확정 전 최소 검사를 둔다.
- PR #32의 Qwen3-TTS MLX 작업자는 English를 지정하고 참조 WAV/전사 해시를 검증한다. 발화자와 참조 결합을 확인해야 한다. 예전 별도 음성 적응 실험에는 8개 소스 클립, 16회 업데이트, 영어·한국어 생성 샘플 8개와 ASR/WavLM 진단이 있다. 블라인드 음색 평가는 미실시였다. “한국어 합성 샘플은 남아 있고 한국어 음색의 품질은 검증 범위 밖이다. 내일 사용할 정책은 검증 범위가 선명한 현재 영어 작업자를 유지하는 것이다.
- PR #32의 로컬 Chrome 2문장 실험은 브라우저 첫 음성 신호 5.24초, 큐 끊김 0회로 보고됐다. 텍스트 입력, 해당 Mac·설정에서의 한 사례다. 마이크·새 지식·한국어 번역·행사장 음향·EMAGE를 포함한 종단 지연의 기준값으로 일반화하지 않는다. PR #30은 CPU에서 7개 실제 모델/고정 응답 사례와 5개 후속 사례를 기록했고, 번역에서 '인사 증거' 오역 및 개인 의혹에 대한 의미 반전까지 발견했다. 검사 설계의 출발점으로 삼는다.

수집은 다음 순서로 진행한다. (1) 시연 후보 SHA와 PR 병합 SHA 고정. (2) 허용한 코드/문서/평가 보고서와 PR 본문/의사결정 댓글을 오프라인에서 수집. (3) PR 번호, 병합 상태/시각, 부모/병합 커밋, 변경된 관련 경로와 줄을 연결. (4) 하나의 카드에 한 가지 검증 가능한 명제와 조건을 적는다. (5) 현 SHA에서 여전히 참인지 다시 읽고 변경된 진술은 역사 카드 처리. (6) 새 질문 표현과 부정 대조 예를 사람이 보지 않은 시험 세트와 분리해 보관. 도구 예는 git log --first-parent, git show <merge-sha> -- <경로>, gh pr view <번호> --json body,mergeCommit,mergedAt,files, URL의 blob/<40자리 SHA>/...#L... 고정 링크다. 기본 SHA와 시연 SHA 차이가 있으면 버전 차이를 카드에 표시한다. 사람 승인 여부와 에이전트 검토를 구분한다. 로컬 시연의 작동 여부는 체크아웃·플래그·프리플라이트 영수증에 연결하고, 공개 PR의 병합만으로 확정하지 않는다.

기존 QAEntry 해석을 유지하며 topic, aliases_ko/en, claim_kind, additional_sources, supersedes 또는 동등한 필드를 선택적으로 추가한다. 새 필드는 기존 파일 기본값에서 동작해야 한다. claim_kind는 구현 확인, 작성자 명시 이유, 측정, 설계 해석의 네 종류로 활용한다. 근거는 코드에 고정된 링크·PR 본문·평가 보고서와 해당 문장을 각각 매핑한다. 변경될 수 있는 PR 본문/댓글은 정확한 인용 위치와 검토 시점·해시를 보존한다. 실험 수치는 조건·비교 대상·분모·누락을 필수로 둔다. 프로젝트 카드 갱신 14일, 뉴스 48시간, 프로젝트+뉴스 통합 최대 100개, 파일당 300KB, 요약 1,600자와 최대 40 cues라는 기존 검증을 지킨다. 새 fact_kind로 분류한다면 기존 QAEntry의 Literal·일관성 검사와 관련 테스트도 함께 변경한다. 발표용 자료와 검색은 기존 JSON과 파이썬 런타임에서 먼저 구현한다.

**실제 카드 예시.** “문장 단위 음성 스트리밍의 이득과 비용”의 구현 근거는 docs/qwen-mlx-live.md와 #32다. “첫 영어 문장이 확정되면 합성 시작, 답변 나머지는 계속 생성, 브라우저는 공통 오디오 시계를 사용”은 확인 사실이다. #32에서 본 5.24초는 텍스트 입력 2문장, 해당 장비 조건의 관측이다. “오래 말할 때 초반 대기를 줄일 수 있다”는 구조적 해석, “다른 모든 TTS보다 빨라 이 모델을 골랐다”는 뒷받침되지 않은 주장이다. “왜 문장별로?”에 답할 자료를 권한 내에서 확보하고, 직접 측정하지 않은 개선폭은 말하지 않는다. #24가 문서화한 '추가 모델 호출 없이 질문 길이·구조를 선택'과 '짧은 첫 문장에 필요한 합성량 감소는 가설'도 서로 다른 문장으로 저장한다. '왜 Qwen?'은 로컬 MLX 경로와 실제 시험에서 사용한 구성은 설명하되 선택 동기는 PR에 작성자가 직접 밝힌 부분만 팀의 판단으로 돌린다. “왜 상반신을 하나의 메시로?”는 #27가 제시한 목/어깨의 연속된 표면이라는 설계 목표와 '당시 upper-body 학습·export 미실행'을 함께 싣는다. 확인하지 않은 현재 학습 상태는 재검토해야 한다.

## 4. 질문 분류, 검색, 말투와 검증

1. 원어 전사와 언어 힌트를 보존한다. NFKC, 대소문자, 한국어 공백/조사, Qwen/큐웬/퀀·RAG/랙 등 리허설에서 실제 나온 표기를 제한적으로 정규화한다. 원문을 영어로 번역해야만 검색되도록 만들면 번역 장애가 질문 경로까지 확대된다. 주제 사전과 이중언어 aliases를 먼저 쓴다.
2. 도메인과 답변 목표를 두 축으로 판정한다. 프로젝트/인물 인터뷰/현재 회사 뉴스/복합/불명확과 소개/구현/이유/비교/결과/한계를 구분한다. '젠슨, 우리 팀은 왜 Qwen을 썼어요?'의 '젠슨'은 호칭이다. '젠슨 페르소나를 어떻게 구현?'은 프로젝트, '젠슨은 실패를 어떻게 생각?'은 인터뷰다. 단순 모델 이름이 사람의 과거 발언 증거를 가로채지 않게 주어, 대상, 질문 표현을 함께 본다. 애매한 '왜 그렇게 했어요?'는 직전 **사용자** 질문의 topic과 출처 ID를 따라간다. 새 관객과 새 세션이면 “Do you mean the team’s choice of model or Jensen’s approach to decisions?”처럼 짧게 되묻는다. 과거 모델 답변이 새 근거가 되어서는 안 된다.
3. 소개 intent는 '무슨 프로젝트예요?', '한 줄 소개', '여기서 뭘 볼 수 있어요?', 'What did you build?', 'Walk me through this demo' 같은 표기를 overview topic에 직접 맵핑한다. 아키텍처/트레이드오프/왜 등 각 intent는 관련 카드군으로 좁힌 뒤 정확한 주제명, 별칭, 단어 겹침/필요시 가벼운 문자 n-gram으로 순위를 매긴다. 동점 ID 사전순을 관련성 대용으로 쓰지 않는다. 질문의 '왜'는 해당 기술의 이유/장단점 카드, '비교'는 양측을 우선 제공한다. 확인된 한 주제에 최대 3장, 복합은 주제별 1~2장 및 전체 토큰 예산을 유지한다. 자료 없는 구체 질문에 일반 소개 카드를 무조건 붙이지 않는다. 상위 후보와 준우승 후보가 다른 주제이고 충분한 차이가 없으면 알려진 한계 또는 확인 질문을 낸다. 임계값은 기존 개발 질문으로 조율한 후 미사용 질문으로 고정 평가한다. 대규모 임베딩 서버·새 파인튜닝은 리허설 후 별도 비교 실험으로 제안한다.
4. 말투는 답이 만들어지는 방식을 설명하는 수단이 아니라 실제 답변에 적용한다. 질문 핵심에 먼저 답하고, 작동 원리를 구체적으로 설명한 뒤 선택의 장점과 대가 하나를 든다. 직접 인용처럼 들리는 캐치프레이즈, 과도한 1인칭 개발 당사자 표현, NVIDIA의 보증은 피한다. 사실/수치/성능은 프로젝트 자료에서 얻고, 직접 인물 질문은 날짜 있는 공개 인터뷰를 사용한다. 명확한 혼합 질문은 두 짧은 절로 나눠 각 출처를 표시하거나 시간 한도상 한 쪽을 먼저 답하고 누락을 밝힌다. PR #29의 선택형 graph는 일괄 켜지 않는다. 관련 파일럿은 strict value application의 순이득을 보여주지 않았다. 매 카드가 사실에 포즈나 인간의 심리를 추가하지 않게 한다.
5. “왜?”의 처리 우선순위는 의도 원문→근거에서의 공학적 추론→불명 순이다. 작성자가 밝힌 이유가 있으면 'The team documented…'. 없고 확인 사실에서 타당한 해석이 가능하면 반드시 영어 음성으로 'One plausible engineering reason is…' 또는 'My interpretation is…'라고 말한다. 자막에는 '가능한 기술적 이유는…'를 유지한다. UI의 작은 라벨만으로 추정을 구분하지 않는다. 비교 우위·성능 격차·사적 동기를 만들어서는 안 된다. 자료도 추론 근거도 약하면 덧붙이지 않는다. 이전 고정 답변을 제거할 때 semantic guard를 대체하지 않고 단순 자유생성을 열지 않는다. MCCCD 미검증을 재현 실패/성공으로 단정하는 고정 회귀 사례는 계속 시험한다.
6. P0의 현실적인 방식은 자주 물을 8~12개 주제에 검수된 영어 첫 문장·KO 대응 자막을 두고, 방향이 확인된 후 보조 문장 1~2개를 생성하는 것이다. 새 질문을 FAQ로 강제 치환하지 않는다. 추정은 허용된 근거 ID와 사전에 허용한 판단 유형을 지원하는 짧은 문장으로 생성한다. 음성 commit 전 영어, 허용 ID, 수치와 조건, 추정 표지, 팀/인물 주어를 검사하고 실패하면 해당 카드의 검토된 짧은 문장으로 복귀한다. ID 일치만으로 의미가 검증되지는 않으므로, 말한 문장 단위의 사람 검토를 리허설 합격조건으로 둔다. 인용 마커와 내부 상태 문자열은 TTS/번역 입력에서 빼고 화면의 출처 서랍과 내부 턴 진단에 둔다. 질문에 맞춘 설명이 가능하도록 단순 소개는 1~2문장, 아키텍처·비교는 2~4문장, 짧게/자세히 요청은 기존 정책 재사용을 검토한다. 첫 문장을 빨리 말하려고 감사 단계를 생략하지 않는다.

**제안 영문 생성 지시문.** “You are the disclosed Jensen Huang AI avatar presenting the student team’s project. Answer the audience’s question in English. For project facts use only the supplied project records. Lead with the mechanism in ordinary spoken language. Explain a trade-off when it answers the question. Say ‘the team’ for the team’s work. Describe a motive as documented only if a record explicitly attributes it to the team. If the records support a plausible engineering interpretation, say ‘One plausible engineering reason is …’ aloud and state the supporting design property. Do not invent comparative results, training history or first-hand involvement. Attach only supplied source IDs. When the question concerns Jensen’s public views, use only the selected dated interview evidence. Preserve uncertainty.” 긴 공통 프롬프트를 다 붙이지 말고 실제 라우트에 필요한 절만 토큰 예산에 넣는다.

**예상 답변, 검토 전 예시.** 관객이 “왜 목소리를 문장 단위로 생성했나요?”라고 물으면 “The system can start speaking once its first English sentence is ready. One plausible engineering reason is shorter perceived waiting, though the player then has to keep gaps between sentences under control.” 자막은 “첫 영어 문장이 준비되면 음성 재생을 시작할 수 있습니다. 가능한 기술적 이유는 관객이 느끼는 대기 시간을 줄이는 것입니다. 다만 재생 과정에서 문장 사이가 끊기지 않게 해야 합니다.” 출처는 #32와 지연 측정 가이드다. 문장 설계의 효과를 수치로 말하려면 같은 기기의 비교군과 해당 수치가 든 별도 카드가 필요하다.

## 5. 영어 음성과 한국어 자막의 결함 격리

- 사용자 언어는 ASR에만, answer_language=en은 생성·speech·replay에, subtitle_language=ko는 표시 경로에만 사용한다. 기존 ChatRequest는 answer_language가 아닌 language 필드를 사용하므로 실제 wire 형식은 {language:"en", input_language:"ko"|"en", subtitle_language:"ko"}다. 번역 설정이 꺼지거나 제공자가 429를 내더라도 영어 답과 동일한 참조 음성이 유지되어야 한다. 기본/연구 모드 동작을 변경할 필요 없이 행사 프리셋에서 이 불변조건을 명시한다. live.py의 영어 검사 조건도 현재 'en + 자막 ko'에 결합돼 있으므로 자막 비사용 시에도 프리셋에 해당하는 영어 검사가 살아 있어야 한다. 영어 문장에 고유명사나 표기 혼합이 나오는 정상 사례를 따로 검토한다.
- 번역 공급자는 기존 src/bias/subtitles.py, caption_stream.py, api.py의 segment 단위 인터페이스에 붙인다. Orbit에서 확인된 방법은 text/plain REST 계약이 아닌 Google 웹 경로 translate_a/single + client=gtx + dj=1에 form q를 보내고 sentences[].trans를 이어 붙이는 방식이다. 이 경로를 공식 Cloud Translation Basic API로 부르지 않는다. 팀이 준비한 공식 계정·권한이 있으면 관리형 공급자를 선택한다. 행사 한정 Orbit 호환 모드를 택하면 무인증 웹 인터페이스의 쿼터·응답 변경·행사망 차단을 받아들이고 리허설에서 실제 성공률을 확인한다. 두 방법은 설정·응답 파서·인증이 다르다. Basic v2 구현 시 text 형식·HTML entity decode·부정/수치 보존 검증을 명시한다. 번역만을 위해 녹음·질문 원문·출처 문서·대화 이력을 Google에 보내지 않는다. 확정 영어 답변 문장 하나만 전달하며 이미 검토된 고정 문구는 정확한 로컬 번역을 우선한다.
- 기존 caption_stream의 대기열 4, 최대 segment 32, audio_end 후 250ms 유예는 앱 완료 후 새 관객을 막지 않는 대신 브라우저 큐에 음성이 남아 있어도 늦은 번역이 탈락할 수 있다. 안정화를 위해 기존 결과 표시·turn/segment/sequence·PCM sample offset을 재사용한다. preflight/리허설로 번역 시각과 실제 playhead를 비교한다. 소리가 나올 때까지 번역이 없으면 그 문장의 영어 원문을 'English'로 표시한다. 문장 재생이 끝난 뒤 늦은 자막이 후속 문장을 덮어쓰지 않게 한다. 취소/재질문/마이크 재시작/새 turn/연결 해제 시 이전 작업·상태를 폐기한다. 재생 완료 뒤 번역을 보여 줄 수 있는 장문 기록과 라이브 자막은 구별한다. 외부 서비스 중단 때 검토된 주제는 로컬 자막, 뜻이 검증되지 않은 임의의 새 문장은 영어로 표시한다. 영어 음성까지 끊어서는 안 된다.
- 위험은 중복 ASR 제출, 숫자와 Qwen/RAG/FLAME 고유명사 오인식, 브라우저 마이크 권한 거부·무음·행사장 피드백, 번역 지연/빈 결과/429/인증 실패, 화면 분리 시 자막 누락이다. 진행자는 키보드로 전사를 바로 고칠 수 있어야 한다. 발표용 별도 창을 실제 쓰면 객석 화면에서 KO 자막·시뮬레이션 표시가 읽히는지를 HDMI/프로젝터에서 확인한다. 실제 앱에 그 자막이 없으면 이미 검증된 단일 창을 행사 프리셋으로 택한다. TTS 장애 때 임의의 한국어 브라우저 목소리로 바뀌지 않고 영어 텍스트·가능한 한국어 자막을 표시하며, 참조 불일치이면 음성을 시작하지 않는다.

## 6. 검증 설계와 리허설 판정

**독립 셋.** 카드를 작성한 사람이 고른 예문과 별도 파일에 36개 고정 시험 질문을 둔다. 12개 프로젝트 소개/구조, 8개 이유/비교, 6개 직접 인물 질문, 4개 후속·주제 전환, 6개 혼합/미확인/최신성 통제로 구성할 수 있다. 한국어와 영어를 절반씩 넣되 단순 번역쌍 외에 '이걸 어디에 써요?', 'What exactly am I looking at?', 'Qwen이 GPT보다 낫다는 측정은?', '페르소나를 만드는 방법과 젠슨 본인의 의견은 어떻게 달라요?'와 같은 독립 표현을 포함한다. 각 질문에 expected_route, 허용/금지 카드, 반드시 담을 사실, 추론 허용 여부, 금지 주장, 올바른 fallback을 미리 기록한다. 새 답변을 보고 정답을 바꾸지 않는다. 랜덤 시드/모델/설정/코퍼스 해시/시각을 남기고, 원음 저장 없이 필요시 익명 ID를 쓴다.

**측정 구간.** 발화 중지→전사 표시, 전사 확인→전송(사람 조작), 요청→첫 유효 문장/서버 첫 PCM/브라우저 첫 실제 재생, 재생 시작→한국어 자막, 마지막 문장 완료를 서로 나눈다. 마이크 입력부터 전송 직전에 운영자가 전사를 읽는 시간은 서버 지연에 합치지 않는다. 차가운 시작과 warm을 분리한다. 자막 적시율은 '해당 문장의 실제 재생 구간 안에 대응 한국어가 한 번 이상 표시된 문장 수/실제 재생된 영어 문장 수'로 정의하고, 첫 표시 지연과 첫 음절 근처에 이미 자막이 있던 비율도 기록한다. 영어 fallback과 제외/실패를 분모에서 빼지 않는다. 기록할 항목은 route, 검색된/사용된 ID, 이유 출처 수준, LLM·음성·번역 공급자 상태, timeout/queue drop, 브라우저 오디오 underrun·취소후 잔여음·전사 실수다. 저장된 텍스트 자동 검사와 두 언어 가능한 검토자의 청취를 함께 한다.

| 시점(KST, 행사 시작을 T로 둠) | 구현/운영 책임 | 종료 조건 |
|---|---|---|

합격 판정은 시연 수준별로 나눈다. 영어 음성·KO/EN 마이크·한국어 자막·주요 프로젝트/인물 질문이 모두 통과하면 전체 시연. 외부 번역망만 실패하면 검수한 발표 질문은 로컬 KO 자막으로 계속하고 자유질문은 영어자막으로 낮춰 이를 안내한다. 마이크가 실패하면 타이핑으로 질문을 받되 마이크 데모의 성공으로 기록하지 않는다. 잘못된 인물 음성, 사실을 꾸미는 이유 설명, 타인 질문의 자막·오디오가 넘어오는 오류가 남으면 해당 자유생성 라이브 시연을 중단하고 검토된 자료/답변을 제시한다. 계획 범위 밖의 신규 모델 도입·음성 재학습·평가 코퍼스 변경·Sophon 웹소켓까지 동시 통합은 행사 후 별도 트랙으로 두고, 이번 발표에서 직접 확인한 구성만 설명한다.

## 8. 발표 후 프로젝트 RAG 확장

발표용 8~12개 필수 주제는 우선 완성한다. 36~44개 검토 카드는 확장 목표로 잡고, 리허설을 줄여 가면서 수량을 채우지 않는다. 이후에는 넓은 자료 수집과 실제 답변에 사용할 지식 공개를 분리한다.

| 층 | 수집과 저장 | 답변에 쓰는 조건 |
| --- | --- | --- |
| 원본 | 기본 브랜치 문서·코드 주석·설정 예시·보고서, 머지 PR 본문과 근거가 있는 리뷰, 커밋 이력·태그를 SHA와 함께 증분 수집. 첫 패스는 해당 9개 영역의 후보 100~250건을 살펴보는 상한으로 둔다. | 원본은 검색 후보와 편집자의 근거로 사용. 내부 메모, 비밀값, 원본 음성/전사, 공개 권한이 없는 자료는 수집 범위에 넣지 않는다. |
| 결정과 사실 | 재현 가능한 단계, 팀이 명시한 선택 이유, 측정 조건, 대안, 보류된 실험을 원자적 카드로 변환. 원본을 여러 장 복제하지 않고 `supersedes`와 적용 버전을 기록한다. | 문장마다 근거, 적용 리비전, 검토 상태가 있을 때만 팀에 관한 사실로 사용. 바뀐 문서는 한 번에 낡은 카드를 비활성화하고 새 카드를 활성화한다. |
| 검색 인덱스 | 안정적인 주제 ID, 한영 별칭과 제품 이름, 검색용 한국어·영어 요약을 추가. 기존 키워드 기준을 먼저 저장하고 늘어난 후보에 대해 BM25·문자 n-gram과 다국어 임베딩을 같은 질문으로 비교한다. | 인덱스는 같은 승인 카드를 반환한다. 다국어 검색의 비용·지연·한국어 구어체 재현율을 보고, 개선이 재현될 때만 하이브리드 검색을 켠다. 카드 최대치 변경은 검토 범위·예산과 별도 검증을 붙인다. |
| 운영 갱신 | 관련 파일이나 PR이 바뀌면 영향을 받는 카드와 시험 질문을 작업 목록에 낸다. 원본 해시로 중복을 제거하고 변경된 카드만 재검토한다. | 승인된 버전은 읽기 전용으로 준비하고 전환한다. 시연 중 장애가 있으면 직전 승인 버전으로 되돌린다. |

확장 평가에서는 한국어 표현 변형, 언어 혼합, 예전 버전을 지정하는 질문, 현재 구조를 묻는 질문, 자료가 부족한 질문을 따로 집계한다. 검색 상위 3장에 필요한 근거가 들어간 비율, 잘못된 도메인으로 빠지는 비율, 생성 답변의 주장별 근거 지원율을 함께 본다. 예시 개수는 수집 상한과 계획 목표다. 성과는 승인된 주제의 커버리지와 독립 질문의 결과로 판단한다.

### 음성과 자막 구현 근거

- 젠슨 황 음성 실험 기록에 16회 LoRA 업데이트와 한국어 합성 WAV가 있다. 한국어 WAV는 평가 출력이며, 별도 한국어 음성 학습 완료나 발표 품질을 입증하지 않는다. 사람 청취 평가는 없었다. 발표용 큐원 MLX 워커는 `lang_code="English"`로 고정돼 있다. [음성 실험과 평가](https://github.com/Dindb-dong/who-is-your-bias/blob/8a9d901cb6a168d4fe8de59086705a8bedadd115/docs/jensen-voice-adaptation.md#L211) · [라이브 음성 워커](https://github.com/Dindb-dong/who-is-your-bias/blob/8a9d901cb6a168d4fe8de59086705a8bedadd115/tools/realtime/qwen_mlx_voice.py#L70)
- Orbit은 서버 API 키 없이 웹 번역 엔드포인트 `translate.googleapis.com/translate_a/single`에 폼으로 `q`를 보내고 `sentences[].trans`를 합친다. 이 프로젝트에서는 회신 문장 단위로만 호출하는 데 참고할 수 있다. 직접 구글 연결을 끄면 기존 로컬 번역 또는 영어 자막으로 돌아가는 옵션을 둔다. Orbit과 달리 실시간 답변에는 12초 대기를 그대로 가져오지 않는다. Orbit의 로컬 `TranslationEngine.swift` 구현
- 정식 Cloud Translation Basic v2는 인증과 결제 연결이 필요하다. 기본 NMT 첫 월 50만 문자는 월간 크레딧으로 상쇄된다. 이미 승인되고 준비된 계정이면 정식 API를 사용할 수 있다. 이번 조사에서는 두 구글 경로 모두 실제 번역 호출을 하지 않았다. [설정](https://docs.cloud.google.com/translate/docs/setup) · [정식 REST 계약](https://docs.cloud.google.com/translate/docs/reference/rest/v2/translate) · [가격](https://cloud.google.com/products/translate/pricing)

### 발표 직전 운영자용 카드

1. 실제 실행하는 웹 주소와 Git 커밋, 발표 모드, 합성 엔진, 자료 묶음 버전을 한 장에 기록한다. 개발 환경의 기능 목록과 혼용되기 쉬운 실험은 현재 상태를 별도로 확인한다.
2. 시작 전에 한국어로 프로젝트 소개, 영어로 아키텍처, 한국어로 모델 선택 이유, 한 문장 속 한영 혼용, 자막 네트워크 장애를 한 번씩 돌린다. 녹음 텍스트를 확인할 수 있는 경로는 `?present=1&reviewQuestion=1`이다.
3. 자막 장애가 생기면 영문 원문 자막을 유지하고 계속 진행한다. 마이크가 오인식하면 질문을 진행자가 교정한다. 실제 음성이나 모델까지 멈추면 팀이 한국어로 이어서 답한다.
4. 발표 예비안은 프로젝트 개요, 아키텍처, 모델 선택 근거, 평가 한계 네 답변을 미리 검토한 영문 문장과 한국어 자막으로 저장하는 것이다. 재생 시에는 준비된 답변임을 표시한다. 전체 리허설 시작 전에는 벡터 DB, 새 모델, 음성 재학습처럼 발표에 직접 필요한 범위를 넘는 변경을 멈춘다.
